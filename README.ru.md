MCP-сервер, который позволяет LLM (Claude Code, Claude Desktop и др.) управлять **запущенным экземпляром Dungeondraft** (размещать объекты, рисовать стены, просматривать карту) через GDScript API для модов Dungeondraft.

У Dungeondraft нет встроенного сервера, к которому можно подключиться, поэтому проект состоит из **двух частей**, которые общаются через локальный сокет:

```
Claude / MCP-клиент
      │  MCP (stdio)
      ▼
server/   ── MCP-сервер на Python  (этот репозиторий)
      │  построчный JSON поверх TCP  (127.0.0.1:8787)
      ▼
mod/      ── мод Dungeondraft  (GDScript, работает внутри DD)
      │  вызовы API для модов
      ▼
   открытая карта  (Objects, Walls, Levels, …)
```

Мод открывает TCP-сервер внутри Dungeondraft и опрашивает его каждый кадр из хука `update(delta)`; сторона Python представляет каждую возможность как инструмент MCP и пересылает вызовы в виде JSON. Формат обмена описан в [PROTOCOL.md](PROTOCOL.md) (на английском).

> **Статус: работает.** Проверено от начала до конца с Dungeondraft на **Godot 3.4.2**: обычный TCP работает из песочницы модов, запасной вариант не нужен. 101 инструмент: запросы, создание, расстановка, изменение, ландшафт, вода, материалы, уровни, слои, проверки планировки и сцены, пакеты ассетов, файлы карт, импорт и экспорт VTT, выделение, снимки, камера, история и работа с файлом карты, а также запасной выход к собственному API и интерфейсу Dungeondraft (см. ниже).

## Что может ИИ

- **Просмотр:** `ping` (также сообщает, приостановил ли пользователь правки ИИ), `get_status`, `list_levels`, `list_elements`, `get_element`, `list_asset_categories`, `list_assets` (с поиском по подстроке), `get_terrain` (считывает нарисованный ландшафт обратно в виде сетки весов слотов).
- **Пакеты ассетов:** `preview_assets` (один контактный лист с ассетами-кандидатами, до 32 штук, чтобы посмотреть на них, прежде чем размещать; `true_scale` показывает их относительные размеры), `list_asset_packs` (какие пакеты установлены и какими из них эта карта действительно может пользоваться: Dungeondraft привязывает пакеты к каждой карте, и карта, созданная без них, молча видит лишь ~1800 базовых ассетов), `search_pack_contents` (поиск по словам и тегам внутри всех установленных пакетов, включая те, которых у карты нет, без чтения самой графики) и `prepare_map_with_packs` (записывает копию карты с дополнительными пакетами и открывает её). `inspect_map_file` даёт сводку по файлу `.dungeondraft_map`, не открывая его: нужные ему пакеты, количество элементов по уровням, самые используемые текстуры, двери, у которых флаг «закрыта» противоречит названию; `compare_to` сравнивает два файла.
- **Создание:** `place_object`, `draw_wall`, `draw_path`, `add_light`, `add_portal`, `add_roof`, `add_text`, `place_pattern` (узорные полы: доски, плитка, кирпич; рисуются под объектами), `build_room` (замкнутая стена и подходящий к ней пол по одному общему контуру, как при совмещённой обводке в интерфейсе), `import_image` (встраивает PNG/JPG/WEBP с диска как объект: собственный реквизит, раздаточные материалы или целую боевую карту в качестве подложки; пиксели хранятся в карте), `scatter_objects` (рощица или россыпь обломков одним вызовом, не задевая стены и дверные проёмы), `place_objects` (много объектов в заданных точках одним вызовом), `arrange_objects` (ряд полок вплотную к стене, стулья вокруг стола, предметы на письменном столе, подогнанные под то, что каждый ассет на самом деле рисует), `list_prefabs` / `place_prefab` (сохранённые группы Dungeondraft), `generate_dungeon` (планировка подземелья или пещеры из Map Wizard одним вызовом), `set_trace_image` (эталонное изображение поверх карты для обводки). `build_room` переиспользует стену, которая уже стоит на границе, поэтому две соседние комнаты делят одну стену, а дверь между ними открывается в VTT.
- **Ландшафт:** `set_terrain_slot`, `fill_terrain` (весь уровень), `fill_region` (прямоугольник или многоугольник, например пол одной комнаты), `paint_terrain` (мягкая кисть), `paint_path` (плавный непрерывный мазок вдоль ломаной: дороги и тропы). По умолчанию слоты 0–3; `set_terrain_slot(..., expand=True)` включает на уровне слоты 4–7.
- **Вода и материалы:** `draw_water` (озёра, реки и рвы в виде прямоугольника или многоугольника, с береговой линией и градиентом глубины; `erase` вырезает острова) и `draw_material` (лава, лёд, булыжник и другие текстуры кисти материалов по прямоугольнику или многоугольнику на выбранном слое).
- **Пещеры:** `dig_cave` прокладывает пещеры и туннели вдоль пути (кисть пещер: вырезает проходимый пол в скале, автоматически добавляя каменные стены и обломки; `dig=false` засыпает обратно; при желании можно задать оттенки пола и стен), `clear_caves` очищает весь слой пещер.
- **Редактирование:** `move_element`, `move_elements` (несколько элементов на одно и то же смещение), `modify_object` (масштаб, поворот, цвет, тень, отражение, блокировка света), `modify_wall` (меняет форму или вид стены; двери и окна остаются на месте и следуют за своим сегментом), `modify_light`, `modify_text`, `duplicate_object`, `delete_element`, `delete_elements`, `select_elements`, `clear_selection`. `set_map_style` задаёт износ построек и стиль линий сетки для всей карты; `set_map_size` меняет размер карты в клетках, как собственное окно Change Map Size в Dungeondraft, а `crop_map` оставляет окно клеток, обрезая карту с любой стороны, и сначала показывает, что будет удалено. Инструменты размещения принимают `snap=True`, чтобы попадать в сетку пользователя, включая шестиугольную или изометрическую сетку мода Custom Snap Mod от Lievven, когда тот загружен; `get_snap_settings` считывает её настройки.
- **Уровни:** `add_level`, `set_level`, `rename_level`, `clone_level` (копирует этаж целиком, чтобы начать с него следующий), `delete_level`, `reorder_levels`, `compare_levels` (показывает другой этаж полупрозрачно под текущим, чтобы всё совместить), `configure_level` (окружающий свет для сумеречных и ночных сцен, включение и выключение освещения, видимость и смешивание ландшафта, береговая линия воды).
- **Слои:** `list_layers`, `set_element_layer` (решает, что чем перекрывается: ковёр под столом, крона над тропой), `add_layer`; `place_object` и `import_image` тоже принимают `layer`.
- **Проверки планировки:** `get_asset_footprint` (настоящий размер ассета, прежде чем выбирать масштаб), `check_object_placement` (проверить место: не пересекает ли стену, не загораживает ли дверь, не накладывается ли на что-нибудь?), `validate_layout` (проверить обставленный уровень), `validate_floorplan` (до расстановки мебели: достижима ли каждая комната, ведёт ли каждая дверь куда-нибудь, есть ли вход), `validate_scene` (голый грунт, на котором ничего не нарисовано, и источники света без видимого светильника), а также `set_spatial_region` / `remove_spatial_region` / `list_spatial_regions` для комнат, зон, которые нужно держать свободными, и защищённого грунта. Инструменты для объектов принимают `check=True`, чтобы сразу отклонить неудачное размещение; правки ландшафта, пещер, воды и материалов не затрагивают область `protected`.
- **Файл карты:** `get_current_map` (путь к открытой карте и идёт ли сохранение), `save_map` (сохраняет в текущий файл, как кнопка Save в DD) и `open_map` (переключает на другую сохранённую карту; отвечает раньше, чем загрузится новая карта, поэтому опрашивайте `get_current_map`; несохранённые изменения отбрасываются без предупреждения, так что сначала вызовите `save_map`).
- **Просмотр результата:** `screenshot` (текущее окно) и `export_map` (чистый рендер всей карты, `grid=False` экспортирует без сетки) возвращают изображения, так что модель может посмотреть на свою работу и доработать её. `set_grid` показывает или скрывает сетку редактора. `export_uvtt` записывает файл Universal VTT `.dd2vtt` (изображение + стены, двери, источники света) для импорта в Foundry или Roll20, а `import_dd2vtt` восстанавливает такой файл на открытой карте: стены, снова соединённые через каждый дверной проём, двери и окна, источники света и окружающий свет, а изображение из экспорта подкладывается снизу для обводки.
- **Камера:** `get_camera`, `set_camera`, `focus_element` (центрирует один элемент), `fit_elements` (вписывает группу в кадр), `reset_camera` (возвращает потерянный вид): наведите вид перед `screenshot`, чтобы рассмотреть конкретное место, например дверь, прорезанную в стене.
- **Нативный доступ:** `native_targets`, `native_describe`, `native_get`, `native_set`, `native_call` дают доступ к собственным объектам Dungeondraft, а `ui_tree` / `ui_action` читают его панели и диалоги и управляют ими. Это нужно для всего, у чего нет отдельного инструмента (плавное смешивание ландшафта, размер кисти, пресет биома). Это крайнее средство: оно обходит отмену, поэтому сначала сохранитесь.
- **Пакет:** `batch` выполняет до 100 вызовов инструментов за один запрос, для длинных серий независимых размещений, как один шаг отмены.
- **Отмена:** мост ведёт собственные стеки отмены и повтора для создания, удаления, перемещения, изменения, слоёв, ландшафта, пещер, воды и материалов, поэтому `undo` / `redo` позволяют модели надёжно откатывать свои изменения (независимо от Ctrl+Z в Dungeondraft). Пакет, разбрасывание, построенная комната, префаб или удаление нескольких элементов считаются одним шагом. `checkpoint` отмечает точку в истории, а `rollback_checkpoint` одним вызовом отменяет всё, что было после неё; `list_checkpoints` показывает открытые контрольные точки. История хранит последние 200 шагов.

На каждый элемент ссылаются по целочисленному `id`; вызовы создания и получения списков возвращают id, которые затем передаются в вызовы редактирования. Координаты заданы в woxel (пикселях мира): `map_center` можно узнать через `get_status`. Ассеты ищите с помощью `list_assets`.

## Установка

**Требования:** [Dungeondraft](https://dungeondraft.net/) (проверено на сборках с Godot 3.4.2), Python **3.10+** и MCP-клиент (например, Claude Code или Claude Desktop). В Windows вместо путей `python3` / `.venv/bin/`, указанных ниже, используйте `python` / `.venv\Scripts\`.

### 1. Установите мод в Dungeondraft

1. На титульном экране Dungeondraft откройте **Mods** и запомните (или задайте) папку модов.
2. Скопируйте `mod/dungeondraft-mcp-bridge/` в эту папку.
3. Включите **MCP Bridge** в списке модов, затем откройте или создайте карту.

После загрузки в журнале Dungeondraft должна появиться строка:

```
[mcp-bridge] listening on 127.0.0.1:8787 (protocol vN)
```

`N` — версия протокола моста; она растёт по мере добавления команд (её также сообщает `ping`).

### 2. Установите MCP-сервер

Устанавливайте в отдельное виртуальное окружение (в большинстве дистрибутивов системный Python управляется извне, а venv сохраняет точку входа чистой и стабильной). Выполните из корня репозитория:

```bash
python3 -m venv .venv
.venv/bin/pip install -e ./server
```

Это установит пакет `dungeondraft_mcp` и создаст точку входа `.venv/bin/dungeondraft-mcp`.

При первом запуске Dungeondraft с модом мод записывает случайный токен в пользовательскую папку Dungeondraft (рядом с `config.ini`); сервер читает его оттуда, так что настраивать ничего не нужно. Управлять вашей картой может только программа, способная читать ваши файлы. Панель **MCP Bridge** в настройках (Settings) Dungeondraft показывает, что делает мост, и содержит элементы управления, которые принадлежат только вам: **Pause AI edits** (приостанавливает правки ИИ; инструменты только для чтения продолжают работать), **Undo the assistant's last step** (отменяет последний шаг ассистента) и переключатель токена.

### 3. Проверьте, что мост работает

Откройте DD, загрузите карту и запустите покомандный валидатор. Он строит небольшую временную сцену около центра карты, печатает PASS/FAIL для каждой команды, а затем удаляет или отменяет всё, что сделал:

```bash
.venv/bin/python server/test_bridge.py
```

Если подключиться не удаётся *и* вы ни разу не видели строку `listening` в журнале DD, значит, песочница заблокировала `TCP_Server`: см. примечание о запасном варианте в PROTOCOL.md.

Проверки планировки — это чистая геометрия, и у них есть собственные тесты, которым не нужны ни Dungeondraft, ни карта:

```bash
.venv/bin/python -m unittest discover -s server/tests
```

Чтобы *увидеть*, как что-то строится (небольшая обставленная комната, которая остаётся на карте, а не тест, убирающий за собой), запустите `.venv/bin/python server/demo_build.py`.

### 4. Подключите MCP-клиент

Зарегистрируйте точку входа по **абсолютному пути**. Для **Claude Code**:

```bash
claude mcp add dungeondraft -s user -- "$PWD/.venv/bin/dungeondraft-mcp"
```

Перезапустите Claude Code, чтобы сервер загрузился (`/mcp` показывает его состояние и инструменты). Или добавьте его в конфигурацию клиента (например, `claude_desktop_config.json` для Claude Desktop), также указав абсолютный путь:

```json
{
  "mcpServers": {
    "dungeondraft": {
      "command": "/abs/path/to/dungeondraft-mcp/.venv/bin/dungeondraft-mcp"
    }
  }
}
```

После этого просите модель, например: *«Каково состояние моей карты в Dungeondraft?»* или *«Покажи несколько ассетов объектов и поставь стул в центр карты»*.

## Настройка

Эти переменные окружения настраивают **сервер на Python** (задайте их там, где MCP-клиент его запускает). Значения по умолчанию совпадают с модом, поэтому они нужны, только если вы меняете константы `HOST` / `PORT` мода в `mcp_bridge.gd`: обе части должны совпадать.

| Переменная окружения | По умолчанию | Назначение |
| --- | --- | --- |
| `DD_BRIDGE_HOST` | `127.0.0.1` | хост, к которому подключается сервер |
| `DD_BRIDGE_PORT` | `8787` | порт, к которому подключается сервер (должен совпадать с `PORT` мода) |

## Расширение

Добавление возможности симметрично: по одному обработчику с каждой стороны.

1. **Мод** (`mod/.../scripts/tools/mcp_bridge.gd`): добавьте `case` в `match` внутри `_safe_dispatch()` и функцию `_my_command(req)`, возвращающую `_ok(...)` / `_err(...)`.
2. **Сервер** (`server/dungeondraft_mcp/server.py`): добавьте `@mcp.tool()`, который вызывает `bridge.request("my_command", ...)`.

Возможность, которая сводится к вычислениям над тем, что мод уже сообщает, живёт только в сервере: у проверок планировки (`spatial.py`), `scatter_objects` и `batch` нет собственного обработчика в моде.

Что стоит сделать дальше: удаление уровня, объединение пакета правок в один шаг отмены и габариты, повторяющие очертания спрайта, а не его ограничивающий прямоугольник.

Пул-реквесты приветствуются. Сначала прочтите [CONTRIBUTING.md](CONTRIBUTING.md) (на английском): там перечислено, что должно входить в законченное изменение и как его проверить.

### Цикл разработки (прочтите, прежде чем править мод)

Есть несколько вещей, которые доставят неприятности, если не знать о них заранее:

- **Мод и сервер перезагружаются по-разному.** Изменения GDScript в `mcp_bridge.gd` вступают в силу, когда вы **перезагружаете мод внутри Dungeondraft** (или перезапускаете DD). Новые или изменённые определения `@mcp.tool()` в `server.py` появляются только после **перезапуска процесса MCP-сервера**; в Claude Code это `/mcp` → переподключить `dungeondraft` (или перезапустить клиент). Установка редактируемая (`pip install -e`), поэтому переустанавливать ничего не нужно, достаточно перезапустить процесс. Для *нового инструмента* нужны **обе** перезагрузки (мод ради обработчика, сервер ради регистрации инструмента); чтобы изменить поведение *существующего* обработчика, достаточно перезагрузить мод.

- **Изучите Dungeondraft, прежде чем писать обработчик.** `native_describe` перечисляет методы и свойства живого объекта, `native_get` читает их, а `native_call` пробует вызвать метод, всё это без перезагрузки мода, так что сначала можно выяснить, что API делает на самом деле. Внутри обработчика отладчика по-прежнему нет: когда вызов DD ведёт себя неожиданно (например, сеттер не срабатывает), **верните промежуточное состояние в ответе**, то есть сохраните значения до и после в отладочном поле, и одной перезагрузки хватит, чтобы увидеть, где меняется значение.

- **Скрипт, который не компилируется, обрушивает Dungeondraft** при загрузке мода, без какого-либо сообщения. Сначала проверьте офлайн, что `mcp_bridge.gd` компилируется; способ описан в PROTOCOL.md («Mod compile errors crash Dungeondraft»).

## Структура

```
mod/dungeondraft-mcp-bridge/   мод Dungeondraft (скопируйте в папку модов DD)
  mcp_bridge.ddmod             манифест
  scripts/tools/mcp_bridge.gd  TCP-сервер + обработчики команд
server/                        MCP-сервер на Python
  dungeondraft_mcp/server.py   определения инструментов MCP
```

## Благодарности

Создано на основе [Dungeondraft Modding API](https://megasploot.github.io/DungeondraftModdingAPI/). Движок — Godot 3.4.2, поэтому в GDScript используются имена сетевых классов Godot 3.

Расширенные слоты ландшафта, редактирование стен, импорт изображений, вода, материалы, инструменты уровней и слоёв, проверки планировки, нативный доступ и доступ к интерфейсу, редактирование света и текста, разбрасывание объектов и пакетные вызовы впервые реализовал Li-Jiaquan в [dungeondraft-mcp-bridge](https://github.com/Li-Jiaquan/dungeondraft-mcp-bridge), форке этого проекта; оттуда они и перенесены.

Отмена целого запроса и обратимое удаление, контрольные точки, инструмент расстановки и общие стены, проверки плана этажа и сцены, список пакетов ассетов, поиск по ним и их подготовка, контактные листы, просмотр файлов карт, импорт Universal VTT, префабы и генератор Map Wizard, стиль карты, собственный Range Dungeondraft для источников света и дверь по умолчанию, токен моста и панель паузы, изменение размера и обрезка карты, а также поддержка Custom Snap Mod впервые реализованы в [battlemap-mcp](https://github.com/thekannen/battlemap-mcp) от [@thekannen](https://github.com/thekannen), переработке этого проекта; здесь они выведены заново по собственному коду Dungeondraft.
